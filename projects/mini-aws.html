01 — THE QUESTION

How can you learn distributed cloud patterns without distributing the learning?

A service is easier to understand when you can see what calls it, what it depends on, and what happens after it finishes.

Cloud experiments can involve credentials, account setup, and real resource costs before the underlying idea is clear. MiniCloud makes a local lab for exploring familiar service concepts—identity rules, instance lifecycle, object storage, network boundaries, and function triggers.

The goal is not to reproduce all of AWS. It is to create a coherent environment where the important seams between cloud services are visible and testable.

02 — THE SYSTEM

One application. Clear service boundaries. Multiple ways in.

The repository describes a Java 17 and Spring Boot modular monolith with a desktop client, a Python CLI, and REST interfaces. Service modules share one runtime while keeping concepts such as IAM, storage, compute, and networking in distinct areas.

03 — ENGINEERING CHOICES

Keep the boundaries visible, especially where trust changes.

01

Use a modular monolith as a learning surface

Service concepts stay in separate packages and interfaces while deployment remains one application. This keeps local setup approachable and the module seams available to inspect.

↗
02

Model authorization as a decision

The policy evaluator returns an allow or deny decision based on the user’s inline and attached policies, making the access boundary a distinct part of the request path.

↗
03

Connect storage events to runtime work

An S3 object event can be matched with enabled triggers and dispatched asynchronously to Lambda execution, linking two modules through an event contract.

↗
04

Constrain the function runtime

The Docker runtime sets container limits such as memory, CPU, process count, a read-only filesystem, and a restricted temporary directory. These are implementation guardrails, not a claim of complete isolation.

↗

04 — WHAT I’M TAKING FORWARD

Systems become intuitive when you can follow the consequences.

The best learning environment doesn’t hide the infrastructure. It makes cause and effect easier to see.

MiniCloud has given me a way to think through how identity, compute, storage, and events meet. It also forced practical architectural questions: where should a module stop, what belongs in an event, and how do we keep local workflows manageable?

Next I’d make the system’s observable paths even clearer: show the request, policy decision, service action, emitted event, and function result together as one trace a developer can follow.
