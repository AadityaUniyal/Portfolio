01 — THE QUESTION

What changes when an audit follows a person’s path?

A page can look correct in its initial state and still become unusable after the first click.

Accessibility checks often begin with the DOM as it exists at load. But keyboard and assistive technology problems can emerge in transitions: opening a dialog, moving through a form, changing routes, or receiving a validation message.

That made the product question specific: can an automated system explore a live interface, reason about what it observes, and keep the trail useful to the engineer who has to decide what happens next?

02 — THE SYSTEM

A loop with a human-readable trail.

The repository connects a browser-based audit flow with analysis, repair verification, and an optional GitHub pull request path. Each stage has a boundary and a place to inspect the output.

03 — ENGINEERING CHOICES

Make exploration inspectable. Keep trust in the loop.

01

Explore from landmarks

Page structure provides a starting point for goal discovery. The recon engine collects visible semantic cues instead of assuming every site has the same journey.

↗
02

Put boundaries around targets

The public audit and repair flows use target policy checks, including URL resolution, before they visit an external page. That boundary matters when a service browses on a user’s behalf.

↗
03

Separate a proposal from proof

Patch verification is a distinct operation from generating a patch. Keeping those steps separate gives reviewers a place to question the change and its observed result.

↗
04

Treat integrations as an explicit action

The GitHub integration route accepts finding and patch details to create a reviewable PR. A generated change should enter an engineer’s workflow with context, not silently rewrite a codebase.

↗

04 — WHAT I’M TAKING FORWARD

Automation is useful when it leaves people more context.

The hard part is not making an agent click. It’s making the result understandable enough to trust, challenge, and improve.

BarrierLens is where I’ve been exploring that end-to-end product problem: browser automation, analysis services, guarded network access, a repair path, and a developer-facing handoff.

The next step I care about is evidence quality: make every finding easier to reproduce, connect it to the exact interaction that exposed it, and help a human reviewer understand the limits of the proposed fix.
